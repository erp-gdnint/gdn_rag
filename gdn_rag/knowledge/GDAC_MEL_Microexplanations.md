| GDAC MEL MICRO-EXPLANATIONS |
| Draft Content and Structure |
| Three short learning units to support grantees across the GDAC lifecycle |

This document contains draft content for three MEL micro-explanations. Each unit follows a consistent structure: why this matters, a plain explanation, a worked example, a practice activity, a reflection prompt, and a short list of further reading for those who want to explore more.

The practice activities are shown as visual mockups of how they will appear in the digital version: drag-and-drop for unit 1, a multiple-choice quiz for unit 2, and a guided story builder for unit 3.

The worked examples are currently placeholders. Real examples from GDN proposals and workshops will be sent before final production.

We have also developed a brief guide for alumni and grantee contributions (audio and video) to support and enhance the examples provided with stories and reflections.

|  |
| :-: |
| MICRO-EXPLANATION 1 OF 3 |
| Outputs and Outcomes |
| Most useful at proposal development and onboarding |

|  |
| :-: |
| WHY THIS MATTERS |

Most project ideas start strong. The challenge is translating that idea into a proposal that shows the logic clearly. If activities, outputs, and outcomes are described using the same terms, or not clearly articulated at all, reviewers have a harder time following the project logic. The same confusion tends to reappear during mentorship check-ins, and again at reporting milestones. Sorting these out early saves time at every stage that follows.

Learning objectives:

Distinguish between activities, outputs, and outcomes in a project plan.

Identify common mistakes teams make when describing what their project produces versus what it changes.

Draft one clear output and one outcome for your own project idea.

|  |
| :-: |
| WHAT THESE TERMS MEAN |

These three terms are connected but describe different things.

|  |  |
| :-: | :-: |
| Activity | What your team actually does. The work, the sessions, the processes. |
| Output | The direct, tangible result of that activity. What was produced or delivered. |
| Outcome | The change that happens because of the project, in people's knowledge, behaviour, or conditions¹[1](#footnote1). |

*Indicators (how you track whether outputs and outcomes are actually happening) are covered in Unit 2.

|  |
| :-: |
| WHAT THIS LOOKS LIKE IN PRACTICE |

The example below is based on a project training community health workers. [Placeholder — to be replaced with a real GDN example.]

|  |  |
| :-: | :-: |
| Activity | Five training sessions delivered to community health workers |
| Output | 50 community health workers complete the hypertension screening training |
| Outcome | Trained workers apply improved referral practices in their communities |

|  |
| :-: |
| WHY THIS DISTINCTION MATTERSOutputs describe what your project produced. Outcomes describe what changed as a result. A common mistake is describing an outcome as if it were an output: for example, writing "improved knowledge among participants" as an output when it is actually the change you are hoping to cause, not the thing you directly delivered.Ask yourself: could I count this directly after the activity ended? If yes, it is probably an output. If it depends on something changing in people or systems, it is probably an outcome. |

Two things teams often struggle with:

|  |  |
| :-: | :-: |
| Watch out for this | Stronger version |
| Writing something like "Improved community health" as an output. This describes a long-term aspiration, not a direct result of a specific activity. It belongs further down the chain as an outcome or beyond. | "50 community health workers complete the hypertension screening training programme." Specific, countable, and directly linked to the activity. |

| APPLY IT TO YOUR PROJECT |

Pick one line from your proposal or project plan and work through these questions.

Is this describing an activity, output, or outcome?

If it is an output, is it measurable and clear but also as relevant as possible to your project goals?

If it is an outcome, can you describe it more specifically? What will be different, and for whom?

| MICRO-EXPLANATION 2 OF 3 |
| Building Useful Indicators |
| Most useful at proposal refinement and early onboarding — build on Unit 1 or use as a standalone |

|  |
| :-: |
| WHY THIS MATTERS |

Indicators that are too vague or too difficult to measure in practice create problems later. During implementation they provide no useful information. During reporting they become a source of back-and-forth between the grantee, the mentor, and GDN. Getting indicators right early does not mean more work. It usually means less, because you are tracking things that actually matter and can actually be measured.

Learning objectives:

Understand what an indicator is and how it differs from an output or outcome.

Recognise the features of a strong indicator: specific, measurable, linked to the change, and realistic.

Improve a weak or vague indicator by making it clearer and more measurable.

Develop at least one practical indicator for an outcome in your own project.

|  |
| :-: |
| WHAT IS AN INDICATOR? |

An indicator is how you track whether an output or outcome is actually happening. It is a specific, measurable way of observing progress: something you can collect data on with the time and resources you have[2](#footnote2).

If you haven't yet explored Unit 1 i (understanding what outputs and outcomes are), it might be a useful starting point, though this unit works on its own too.

|  |
| :-: |
| WHAT MAKES AN INDICATOR USEFUL? |

A useful indicator answers one question clearly: what exactly are we trying to track, and how will we know if we are on track?

|  |  |
| :-: | :-: |
| Specific | Names the change clearly: who, what, in what context. |
| Measurable | You can collect data on it with the time and resources you have. |
| Linked to the change | Tracks the outcome you care about, not just the activity that led to it. |
| Realistic | You know how you would actually collect these data in practice. |

|  |
| :-: |
| WHAT THIS LOOKS LIKE IN PRACTICE |

The first example is based on a project focused on keeping girls in school. [Placeholder — to be replaced with a real GDN example.]

|  |  |
| :-: | :-: |
| Less useful indicator | More useful indicator |
| "Girls' education improved" — Too broad. You cannot track "improved education" directly. It is an aspiration rather than an observable measure. | "Percentage of girls enrolled in participating schools who remain enrolled through the end of the academic year" — Specific, trackable, and directly linked to the outcome. |

It is also worth knowing the difference between two kinds of indicator:

|  |  |
| :-: | :-: |
| Output indicator | Outcome indicator |
| "Number of awareness sessions held": Tells you the activity happened. Useful for tracking delivery, but does not show whether anything changed as a result. | "Percentage of participants who correctly report the referral pathway one month after the session": Tells you whether knowledge actually resulted in change. This is usually the kind of information that your donors and partners will want to know. |

|  |
| :-: |
| WORTH NOTINGAn output indicator like "number of training sessions held" tells you the activity happened, not whether anything changed as a result. It can be useful for tracking delivery, but it should not be the only thing you track. A strong MEL plan includes both output and outcome indicators, they answer different questions. |

|  |
| :-: |
| APPLY IT TO YOUR PROJECT |

Pick one indicator from your proposal or draft MEL plan and work through these questions:

Is it specific? Does it name a particular change for a particular group?

Is it measurable? Do you know how you would collect this data?

Does it track the outcome you care about, or just the activity you did?

Is it realistic within your timeline and budget?

| MICRO-EXPLANATION 3 OF 3 |
| Using Evidence to Tell an Impact Story |
| Most useful at final reporting and dissemination |

|  |
| :-: |
| WHY THIS MATTERS |

Most GDAC grantees are deeply committed to the communities they work with. That comes through clearly. What often takes a message further, to inform or inspire funders, policymakers, or others who could scale or support the work, is being able to pair the human story with clear evidence of what changed.

The people who fund development work often need to justify decisions to their own stakeholders. Data gives them something concrete to work with. A well-told story makes that data meaningful. Both matter, and they can work together rather than competing.

Learning objectives:

Explain what evidence and storytelling each bring to communicating project impact.

Use the five-question framework to structure a simple impact story.

Draft a short evidence-based summary of change from your own project.

|  |
| :-: |
| A SIMPLE FRAMEWORK |

A strong impact story answers five questions. These are the backbone of a final report, a dissemination plan, or any communication about the work after the project ends.

|  |  |
| :-: | :-: |
| 01 What problem were we addressing? | Set the context. Who was affected and why did this matter? |
| 02 What changed? | Describe the actual change in knowledge, behaviour, conditions, or circumstances. |
| 03 How do we know? | Point to the evidence : data, indicators, observations, participant accounts. |
| 04 Why does that matter? | Connect the change to something bigger — the people, the community, the system. |
| 05 What would the situation look like without this project? | The counterfactual. Help the reader understand why this project was necessary and what would not have changed without it³[3](#footnote3). |

|  |
| :-: |
| WHAT THIS LOOKS LIKE IN PRACTICE |

The example below is based on a project working on job readiness skills with young people. [Placeholder — to be replaced with a real GDN example.]

|  |  |
| :-: | :-: |
| Less effective | Stronger impact statement |
| "Participants appreciated the training and found it inspiring." This statement conveys enthusiasm but gives no evidence of what actually changed or for whom. | "The project trained 120 young people in job readiness skills. Three months later, 68% reported having applied for at least one job, and 34% had entered paid work or internships. Participants also described greater confidence in navigating recruitment processes, confidence they said they did not have before." |

|  |
| :-: |
| KNOW YOUR AUDIENCEBefore you write your impact story, think about who will read it. A funder needs something concrete to justify their investment to their own stakeholders. A policymaker needs to understand what this means for the people or systems they are responsible for. A peer researcher wants to know what you found and how you know it.Your story does not change, but the emphasis can shift depending on who you are writing for. The five-question framework works for all audiences. What you choose to foreground in questions 04 and 05 will vary. |

|  |
| :-: |
| A NOTE FOR MIDP AND JSDF GRANTEESDecision-makers often need to justify their choices to their own superiors. Data gives them something concrete to stand on. Your project's story makes them want to act on it. You have both. Use both. |

| APPLY IT TO YOUR PROJECT |

Bring the draft you wrote in the activity above to your closeout meeting with your mentor.

Your final report to GDN requires a 500-word technical brief on your findings and policy implications. These five questions are a strong starting point for that brief.

GDN tracks outcomes through annual surveys for up to two years after the project ends. Your story will matter beyond the grant itself.
